## Introduction

As of TrueNAS Scale 25.10, a new share option is now available NVMe-oF.

> [!TIP]
> NVMe-oF (NVM Express over Fabrics) is a storage protocol that extends high-speed, low-latency NVMe performance from local PCIe slots across a network fabric like Ethernet, Fibre Channel, or InfiniBand, allowing servers to share remote flash storage as if it were directly attached.

If you do have NVMe drives in your TrueNAS Scale server, give this a try. If you have traditional HDDs then there is an iSCSI option with this drive as well. What the driver does is create persistent volumes on demand, and then maps the PVC to the volume for use with the pod. I will be covering the NVMe-oF setup, but the iSCSI option is documented at [QUICKSTART-ISCSI](https://github.com/fenio/tns-csi/blob/main/docs/QUICKSTART-ISCSI.md). While the project does call out that this project is in early development, this is a lab, and the correct place to explore these new technologies.

This guide will walk you through creating the base NVMe-oF Dataset on a TrueNAS Scale server and then creating the NVMe-oF Storage Class on your k8s cluster. At the end, you should be able to spin up pods, and select the `tns-csi-nvme` storage for your PVC `storageClassName`. From a lab perspective, this will give you a closer match to how things operate in the cloud. Any cloud provider will logically map disk to your claims on demand. These claims are independent of the nodes the pods are running on which allows for pods to rebalance across different nodes. In a hope setup, if you're just using LVM disks tied to the nodes themselves, the pods will only be able to reschedule on the node the claim was originally created on.

## Creating an NVMe-oF Port in TrueNAS

> [!NOTE]
> This guide assumes that you are familiar with setting up a TrueNAS Scale server.

* **Versions:**
  * **TrueNAS Scale:**: [25.10.7](https://www.truenas.com/truenas-community-edition/) ( latest community stable )
  * **tns-csi:** [v0.20.0](https://hub.docker.com/r/bfenski/tns-csi-driver/tags)

1. Create Dataset
    * Log into your TrueNAS Scale server
    * Go to **Datasets**
    * Select your root pool or parent dataset that you would like to create your `NVMe-oF` share in and click **Add Dataset** in the upper right hand corner
    * Name your dataset (e.g., k8s). This will be part of the `pool`  name that you will use later
    * Set the Dataset Preset to Generic
    * Click **Save**
2. Setup NVMe-oF port
    * If it is not already running, you will need to go to **System** -> **Services** and enable **Start Automatically** for the **NVMe-oF** service
    * Click on **Shares** -> **NVMe-oF Subsystems**
    * Click **Add Subsystem**
    * In the panel, fill in **Subsystem Name** (e.g., nvme). You won't actually use this namespace, but it is a necessary step to create the port for the service to listen on
    * You can leave **NQN** alone as it will use the global value generated by the service
    * Next to **Namespaces** click **Add**
    * Either key in or use the folder view to browse to the path of your `k8s` dataset you created earlier (e.g., `/dev/zvol/tank/k8s`)
    * Click **Next**
    * This will bring up the Access view. Leave **Allow any host to connect** checked if you're secure with your lab network
    * Next to **Ports** click **Add** -> **Create New**
    * In the **Add Port** window, set the following: **Transport Type:** `TCP`, **Port:** `4420`, **Address:** `<Your TrueNAS IP Address>` (*If you have a basic setup, there should only be one address listed*)
    * Click **Save**
    * In the Subsystems view, you will see a warning next to the Name of the Subsystem you created saying that it is not usable. This is OK and can be ignored. (*In the [QUICKSTART-NVMEOF](https://github.com/fenio/tns-csi/blob/main/docs/QUICKSTART-NVMEOF.md) guide, the steps are a little different, where you were allowed to create the port directly. I suspect the menus have changed slightly between patches on the TrueNAS side.*)
3. Create new user for the API Key
    * From the TrueNAS webUI, select **Credentials** -> **Users**
    * In the top left click **Add**
    * Give the user a meaningful name (e.g., `k8snvme`). Very deliberate and suggests what might break of the account goes away
    * For **Allow Access** uncheck **SMB Access** and check **TrueNAS Access**. Select **Full Admin** from the **Select Role** dropdown
    * For **Password** you can provide a password of your choice. You will not use this password with the driver
    * Click **Save** and the account has been created. As a cleanup task, you can disable the password for that account
      * Select the account name you just created
      * Click **Edit**
      * In the **User Edit** panel check **Disable Password**
      * Click **Save** to confirm the changes
      * This prevents someone from logging into your TrueNAS server under that account
4. Create an API Key for the new user
    > [!TIP]
    > This API key is a secret value and should never be committed to code.
    > When you install the helm chart, you can supply this value and it will
    > generate a k8s secret that will be used with the deployment.
    * While logged in as the TrueNAS_Admin or the account you just created click on that username in the upper right corner of the webUI
    * Select **My API Keys**
    * This will take you to the **User API Keys** window
      * The default view filters for the username you are currently logged in under. So if after you create an API key and you don't see it in this view, make sure you're not filtering it out
    * In the upper right corner of the webUI select **Add**
    * In **Name**, provide a meaningful name (e.g., k8snvme-key)
    * In the **Username** dropdown, make sure you select the username for the account you created
    * Leave **Non-expiring** checked
    * Click **Save**
    * A key will be generated and a new **API Key** window will be displayed with your API Key shown in plain text.
      > [!NOTE]
      > This is the only time the key is shown. If you do not copy it and store it somewhere, you cannot retrieve it.
      > Instead you will have to delete the key and generate a new one.
5. Preparing a values file for the helm deployment
    > [!NOTE]
    > If you're working on macOS or a Linux system that's using `Zsh` as your shell, `Zsh` will treat `[]` as globbing patterns.
    > This will trigger errors like `zsh: no matches found` when trying to instal the `helm` chart is described in the maintainers docs.
    > For ease of testing and reduced syntax you can create a values file instead of supplying all the arguments in the `helm` CLI.
    * Create a `values.yaml` file and populate the values

        ```yaml
        # values.yaml
        truenas:
          url: "wss://<your TrueNAS IP address>:443/api/current"
          apiKey: "<your generated API Key>"
          skipTLSVerify: true # <- This assumes you're using a self-signed cert on your TrueNAS Scale server
        storageClasses:
          - name: tns-csi-nvmeof # <- This is the name you will supply to other CRDs when you need to provision a PVC
            enabled: true
            protocol: nvmeof
            isDefault: true # <- If set to true, this will label the storage class as the default class. If you do not supply a storage class name in a deployment, this value will be used.
            pool: <your ZFS pool created in step 1> # <- (e.g., tank/k8s)
            server: <your TrueNAS IP address>
            transport: tcp
            port: 4420 # <- The port you created in step 2
            parameters:
              # Optional ZFS parameters you can apply that are specific to your use case
              # Note - you can create multiple storage classes with different options.
              # You would then apply these to your different types of PVCs.
              # The below settings are for DB heavy usage, but if you had a service with
              # a lot of big files, you might want to consider increasing the volblocksize to 64K.
              # You will see these settings displayed in TrueNAS under each PVC that is created
              zfs.volblocksize: "8K"
              zfs.compression: "off"
              zfs.sync: "standard"
              csi.storage.k8s.io/fstype: "xfs"
        ```

    * Create the namespace you will deploy the drive into. This necessary for the next step

        ```bash
        kubectl create namespace tns-csi
        ```

    * Update permissions for the namespace. This is necessary for the daemonset to be able to start on all the nodes. If you deploy the chart without this update, will see errors in your daemonset with the pods being unable to start due to policy restrictions.

        ```bash
        # Grant the namespace privileged rights
        kubectl label --overwrite ns tns-csi pod-security.kubernetes.io/enforce=privileged

        # Suppress warnings of pods being deployed into the privileged namespace
        kubectl label namespace tns-csi pod-security.kubernetes.io/warn=privileged --overwrite
        kubectl label namespace tns-csi pod-security.kubernetes.io/audit=privileged --overwrite
        ```

    * Verify the labels have been applied correctly

        ```bash
        kubectl describe namespace tns-csi
        Name:         tns-csi
        Labels:       kubernetes.io/metadata.name=tns-csi
                      name=tns-csi
                      pod-security.kubernetes.io/audit=privileged
                      pod-security.kubernetes.io/enforce=privileged
                      pod-security.kubernetes.io/warn=privileged
        Annotations:  <none>
        Status:       Active

        No resource quota.
        ```

    * Deploy the `tns-csi` `helm` chart

        ```bash
        helm install tns-csi oci://registry-1.docker.io/bfenski/tns-csi-driver \
          --version 0.20.0 \
          --namespace tns-csi \
          --create-namespace \
          -f </path/to/values.yaml>

        Release "tns-csi" has been installed. Happy Helming!
        NAME: tns-csi
        LAST DEPLOYED: Thu Oct 22 10:28:08 2026
        NAMESPACE: tns-csi
        STATUS: deployed
        REVISION: 1
        DESCRIPTION: Install complete
        TEST SUITE: None
        NOTES:
        Thank you for installing tns-csi-driver!
        ```

    * Validate the deployment is running

        ```bash
        # Check that daemon-set has deployed to all worker nodes in your cluster
        # (7 workers in this example)
        kubectl get daemonsets -n tns-csi
        NAME           DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
        tns-csi-node   7         7         7       7            7           <none>          22h

        # Check the controller has successfully deployed
        kubectl get deployments -n tns-csi
        NAME                 READY   UP-TO-DATE   AVAILABLE   AGE
        tns-csi-controller   1/1     1            1           22h

        # Check that you can see the storage class and that it is the default
        # if you configured it as such
        kubectl get storageclasses
        NAME                       PROVISIONER      RECLAIMPOLICY   VOLUMEBINDINGMODE   ALLOWVOLUMEEXPANSION   AGE
        tns-csi-nvmeof (default)   tns.csi.io       Delete          Immediate           true                   22h
        ```

    * You can now deploy additional services and view the persistent volumes



> [!IMPORTANT]
> During the setup of this driver, I ran into an interesting issue. When these
> persistent volumes are created, they are ZVols created on ZFS. A strict
> requirement for this is that the storage request needs to be in binary
> format. What this means is that if you supply a value like `10G` which
> is a decimal format, it will attempt to create a ZVol with the size of
> 10,000,000,000 bytes. The volume will fail to be created with errors saying
> `volume size must be a multiple of volume block size`. Because the block sizes
> are binary (4K, 8K, 16K, 32K...) the requested size needs to be cleanly
> divided by the blocksize. I discovered this issue when trying to install
> the clickhouse charts and buried in a dependency tree somewhere are
> `5G` and `10G` storage request values. The fix was to supply my own
> `5Gi` and `10Gi` values to overwrite the defaults. Once I did this,
> the volumes came right up. If this should happen, you will see the errors
> in both the tns-csi-controller logs, tns-csi-node logs, and on the PVCs
> themselves when describing them.
